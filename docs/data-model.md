# Data model

The database is PostgreSQL, accessed through Ecto. Schemas live in
`lib/mouse_tracker/tracking/` and `lib/mouse_tracker/accounts/`.

## Hierarchy

```
User
├── Experiment (name, description)
│   └── Video (filename, filepath, fps, status, background_frame,
│       │       calibration_id?, subject_id?, dimensions, duration…)
│       ├── ROI                ← many-to-many via `videos_rois`
│       └── TrackingResult (distance_px/cm, speed_mean/median/max,
│           │                thigmotaxis_pct, immobility_seconds,
│           │                path_tortuosity, heatmap_path, speed_profile_path)
│           └── RoiTime (seconds, frame_count)   ← per (ROI, TrackingResult)
├── Calibration (2 scale segments + cm, px_per_10cm, threshold, min_area,
│                peripheral_pct, immobility_threshold_cm, valid_region)
├── ROI (name, shape, geometry)          — user-owned geometry, shared across videos
└── Subject (name, sex, age_days, weight_g, genotype, notes)
                                          — user-owned identity, shared across videos
```

## Reusable, user-owned resources

`Calibration`, `ROI` and `Subject` are **owned by a user and reused across many
videos**, not copied per video. A `Video` links to one `Calibration`
(`calibration_id`), one `Subject` (`subject_id`) and N `ROI`s (via `videos_rois`).

The key invariant: **shared geometry/identity never means shared measurements.**

- A `ROI` row holds only geometry (name/shape/coords). Every measured value lives
  in `roi_times` / `tracking_results` keyed per video, so attaching one ROI to many
  videos produces distinct `roi_times` and distinct heatmaps — no data is
  superimposed.
- The same `Subject` can be tracked across many videos/experiments over time; only
  its identity/metadata (name, sex, genotype, `notes`) is shared, never the
  per-session metrics.

Because a resource can be attached to results, deleting one is guarded: the context
counts videos still using a calibration/subject/ROI and blocks deletion while any
exist (the FK is `nilify_all`, which would otherwise silently orphan results). ROI
geometry is additionally *locked* while attached to a `"done"`/`"processing"` video
(`Rois.roi_locked?/1`) — you rename it or "duplicate ROI" instead of editing the
shape out from under existing results.

## Calibration — two scale segments

`px_per_10cm` (the pixels-per-10cm conversion factor) is derived from **two
independent scale segments** drawn by the user:

- segment 1: `coordinate_x1..y2` + `cage_side_cm`
- segment 2: `coordinate_x3..y4` + `scale_cm_2`

The two derived factors are **averaged**. If they diverge by more than 8%, the
wizard shows a **non-blocking warning** (a single mis-click on one segment can't
silently corrupt the whole conversion — the second segment cross-checks it).

`Calibration` also carries the tracking parameters applied per video:
`threshold`, `min_area`, `peripheral_pct` (thigmotaxis margin, 0–50%),
`immobility_threshold_cm`, and the `valid_region`.

## Video status

`Video.status` tracks processing state, constrained to
`"pending" | "processing" | "done" | "error"`. `background_frame` (default `0`) is
the frame index used to build the background model — pickable in the wizard when
frame 0 is contaminated (e.g. a hand still in the arena).

## Per-user pipeline defaults

`User` carries optional defaults — `default_threshold`, `default_min_area`,
`default_peripheral_pct`, `default_immobility_threshold_cm` — that prefill the
wizard's Advanced step. A blank field falls back to the built-in defaults
(threshold 80, min area 250, peripheral 20%, immobility 2 cm/s), which also mirror
the Python engine's fallbacks.

## Auth

`User` + `UserToken` back magic-link and password auth (generated by
`phx.gen.auth`). Tokens carry a `context` (`"session"`, `"login"`,
`"change:email"`). `Scope` wraps the current user and is threaded through the
context functions for ownership checks.
